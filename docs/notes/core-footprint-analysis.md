# 核心包、核心加载与空闲内存：原因和解决方案

本文记录 `bc688b2` 的原因分析阶段；后续已实现的改动与复测单独记录在[最小修复](./core-footprint-simple-fix.md)，下文基线数据不覆盖更新。

日期：2026-09-09。分析对象为 Jieshu `bc688b2` 与本地 Wujie `c459329`。本轮先完成原因分析和方案验证，核心源码没有改动。完整包的 SHA-256 与上一轮正式测试完全一致；下述构建替换实验仅在内存中应用候选变更。

三个指标有关联，但不能归结成一个问题：**较多的功能代码使包更大、后台解析更多、代码常驻更多；此外还确认了操作记录不释放和弱表空容量两个可单独处理的内存问题。**

目前没有已经验证能在保留全部行为的同时，让这三个指标全面达到 Wujie 水平的方案。小规模去冗余有确定收益，但只减少约 0.2 KB gzip；大幅缩减需要继续重构必经实现，或引入有明确成本转移的可选分包。不能把删掉隔离和取消保障当成无损优化。

## 1. 核心包为什么大

统一使用 Vite 8.2.2、生产压缩、ES2018、IIFE，从两份本地源码构建；不是拿两种发布构建配置比较。

| 构建                                     | Wujie raw / gzip（B） | Jieshu raw / gzip（B） | 说明                               |
| ---------------------------------------- | --------------------: | ---------------------: | ---------------------------------- |
| 全部公开运行时导出                       |       65,660 / 19,802 |       108,681 / 32,759 | raw 多 43,021 B，gzip 多 12,957 B  |
| ESM 消费者只导入 startApp，再打同样 IIFE |       64,115 / 19,461 |       103,112 / 31,390 | 摇掉未用 API 后，raw 仍多 38,997 B |
| ES2022 全包诊断实验                      |       62,967 / 19,165 |       103,759 / 31,345 | 只用于量化降级成本，未修改兼容目标 |

生产产物没有第三方运行时依赖拖大体积。Jieshu 只导入 startApp 可以减少 5,569 B，控制器等公开 API 的附带成本存在，但不是主因。ES2018 相比 ES2022 的额外降级成本，两边相差 2,229 B，只解释原始差距约 5.2%；提高 target 既不能解决主要问题，也会改变兼容要求。

用压缩后 source map 的生成区间分配字节，并按拆分前后职责合并文件，主要增量如下。映射字节全部加总与完整 bundle 一致，但模块归属仍是近似值，不等于删除它能节省的字节，也不能把各模块 gzip 相加。

| 职责及文件                                                        | Wujie 映射字节 | Jieshu 映射字节 |   增量 | 已核对的行为增量                                                        |
| ----------------------------------------------------------------- | -------------: | --------------: | -----: | ----------------------------------------------------------------------- |
| template + entry                                                  |          6,674 |          17,717 | 11,043 | HTML 上下文解析、属性保留、fetch 身份与缓存作用域隔离、过期待决请求处理 |
| effect + effect-pipeline                                          |          6,643 |          13,444 |  6,801 | 动态资源所属实例检查、取消、脚本队列与 DOM 操作兼容                     |
| iframe + iframe-script + iframe-inline-events                     |         14,109 |          20,468 |  6,359 | 模块脚本完成、取消、跨 realm 判断、内联 DOM 事件隔离                    |
| sandbox + sandbox-runtime + index + controller + operation-intent |         11,304 |          24,305 | 13,001 | 启动取消、异步卸载、重入处理、控制器和调度协调                          |

这些是代码职责差异，不代表每一字节都不可优化。但把完整 HTML 解析直接换回较短的正则，或者删除异步恢复点的有效性检查，会改变已有边界行为，需要逐项证明等价。

证据：[bundle-analysis.json](../../benchmarks/comparison/results/2026-09-09-footprint/bundle/analysis.json) 和 [module-differences.json](../../benchmarks/comparison/results/2026-09-09-footprint/bundle/module-differences.json)。

## 2. 核心加载为什么慢

新诊断只加载核心，不挂载子应用、不安装原 benchmark fixture；每条使用独立 browser context，交错两框架。显式 UTF-8 与原来的未声明 charset 各测 30 次/框架，共 120 次。计时后再 GC，trace 另跑，避免将 trace 开销混入常规样本。

| UTF-8，CPU 1x，中位数        |     Wujie |    Jieshu |
| ---------------------------- | --------: | --------: |
| 核心 script 加载至 onload    |   3.30 ms |   4.40 ms |
| 请求开始至响应结束           |   1.00 ms |   1.00 ms |
| 响应结束至 onload            |   1.80 ms |   2.85 ms |
| CDP ScriptDuration 增量      |  0.281 ms |  0.492 ms |
| 加载后 GC 堆相对加载前的增量 | 161,244 B | 217,420 B |

本机 HTTP 的请求响应耗时中位数相同，额外耗时主要出现在脚本处理阶段。响应结束至 onload 包含执行与调度，不能直接叫纯解析时间。

再用带精确核心脚本 URL 的完整 trace 事件核对，每框架 3 次：

| UTF-8 trace 中位数            |    Wujie |   Jieshu |
| ----------------------------- | -------: | -------: |
| 后台解析 v8.parseOnBackground | 1.293 ms | 2.367 ms |
| EvaluateScript                | 0.416 ms | 0.638 ms |
| v8.compile，streamed=true     | 0.024 ms | 0.022 ms |

这支持“更多源码需要更多后台解析和模块初始化”的解释。仅看 Performance.V8CompileDuration 会漏掉流式后台解析，不能据其约 0.013 ms 相同就说编译成本持平。Trace 只有 3 次且会增加开销；这些事件可能嵌套或重叠，不能相加成完整加载时间，也没有精确分摊每个模块造成的毫秒差。

UTF-8 下纯加载堆差为 **56,176 B**；未声明 charset 被 Chromium 识别成 windows-1252，其相对差为 56,184 B，仅相差 8 B。两边 DOM/监听计数相同。因此，在本夹具中，**编码不是空载内存劣化的主因**。绝对堆包含测量上下文，不与上一轮夹具的绝对值直接相减。

证据：[load-summary.json](../../benchmarks/comparison/results/2026-09-09-footprint/load/summary.json)、[120 条观测](../../benchmarks/comparison/results/2026-09-09-footprint/load/observations.jsonl)、[trace 明细](../../benchmarks/comparison/results/2026-09-09-footprint/load/trace-summary.json)。

## 3. 空闲内存的三个来源

### A. 源码与编译代码常驻：主要的固定差距

上一轮最终销毁并静置后的 JS heap 中位数为 Jieshu 3.238 MiB、Wujie 2.922 MiB。阶段诊断堆快照则按 V8 节点 self_size 归因：总差 407,159 B，其中代码类别多 258,216 B，已沿引用边确认的核心源码外部存储多 85,774 B。两项合计约占该快照差值 84.5%。

这里的 self_size 不是 CDP JSHeapUsedSize、retained size 或浏览器 RSS，不能将这些数字与约 0.316 MiB 的正式差值混算。历史快照也早于本轮提交，具体 bundle 和节点哈希均保留在[原堆归因](../../benchmarks/comparison/results/2026-09-09-optimized/heap-attribution.json)中。本轮纯加载复测再次确认约 55 KiB 的固定增量。

这部分不会通过 destroyApp 或 clearAssetsCache 自动消失；减少需要加载和执行的代码，才能从根本上减少它。只做缓存清理不能解决。

### B. 操作记录按应用名累积：已确认的可增长状态

[operation-intent.ts](../../packages/jieshu-core/src/operation-intent.ts) 把操作记录保存到共享的 `__JIESHU_CORE_INTENTS` / `__JIESHU_INJECT.coreOperationSlots`。begin/observe 会添加或替换，完成后没有删除。公开 destroyApp 也会创建记录，因此对不存在的应用名调用 destroy 仍能积累状态。

本轮用同一源码、UTF-8、两框架各 3 轮，分别对同名和 1,000 个不同名称调用公开 destroyApp，总计 12 个独立 context、12,000 次调用：

| 诊断动作                          | Wujie 操作槽 |     Jieshu 操作槽 |
| --------------------------------- | -----------: | ----------------: |
| 同名销毁 1,000 次                 |            0 |                 1 |
| 不同名销毁至 250 / 500 / 1,000 次 |    0 / 0 / 0 | 250 / 500 / 1,000 |

在没有任何活跃应用的诊断页面，删除 Jieshu 两条全局槽引用并 GC，每轮均释放 **147,216 B（143.77 KiB）**。这只是验证持有来源的干预，**不是可以直接粘到生产中的修复**。

这是未知应用名的空销毁压力测试，不是 1,000 次真实子应用挂载。Wujie 在相同调用下也有约 79 KB 的堆增长但无操作槽，所以不能把全部 heap 增长都解释成泄漏。原基准仅有 6 个槽，快照直接开销下界约 812 B，不能用本问题解释原来全部 0.316 MiB 的差距。另一个“已完成 Promise.race 继续保留销毁回调”的猜测没有复现，不列为已证实泄漏。

证据：[idle-summary.json](../../benchmarks/comparison/results/2026-09-09-footprint/idle/summary.json)、[每轮清理前后差值](../../benchmarks/comparison/results/2026-09-09-footprint/idle/paired-deltas.json)。

### C. 跨 realm 补丁的弱表保留空容量

历史堆快照中，[iframe.ts](../../packages/jieshu-core/src/iframe.ts) 的模块级 `instanceofPatchStates` WeakMap backing table 为 **32,788 B**。表内 2,145 条数据边均是已清除的空洞，没有活跃构造器；子 realm 已被 GC，但表的容量仍保留。

这和强引用住子应用是不同问题。简单给 WeakMap 起个新名字或只删除 peer 条目，不等于释放其全局表容量。其他 sandbox、teardown、unmount hook 注册表在该快照中为空，未发现它们保留已销毁实例。

该项属于历史快照直接证据和当前源码仍存在的结构；本轮未重新采集真实挂载后的完整堆快照，不能把 32,788 B 当成本轮新测的节省。证据及持有链见[内存审计](../../benchmarks/comparison/results/2026-09-09-footprint/idle/AUDIT.json)。

## 4. 解决方案与执行顺序

### 第一步：低风险去冗余，收益已做构建实验

将私有常量对象再解构导出的写法改成同值直接常量；共享 entry/template 完全相同的属性转义函数及属性名数组，保留两个不同的序列化流程。固定源码构建实验的结果为：

| 方案               | raw 节省 | gzip 节省 |
| ------------------ | -------: | --------: |
| 常量扁平化         |    594 B |     188 B |
| 共享转义及属性数组 |    204 B |      10 B |
| 两项合并           |    798 B |     209 B |

两项合并后预期为 107,883 B / gzip 32,550 B。不是两个 gzip 节省简单相加。实验没有修改核心，也还未证明行为等价；落地时需跑属性转义、布尔属性、nonce/media/disabled、原生样式 fallback、类型及现有回归。它能改善体积与固定成本，不能承诺可测的毫秒收益，更不够追平 Wujie。

证据：[构建候选实验](../../benchmarks/comparison/results/2026-09-09-footprint/bundle/what-if.json)。

### 第二步：修操作记录生命周期，消除按名称增长

设计方向是“共享使用计数”：begin/observe 都登记使用，start/refresh 终结、实际 destroy 结束、idle preload 任务结束时各释放一次。只有最后使用者退出，且记录仍属于该操作时，才删除共享槽。

不能只在 destroy.finally 里 delete：destroy 等待期间，新发起的 preload 可能已观察同一个槽；直接删除会误取消合法预加载。旧操作的释放也不能删掉新操作的槽，计数不能放在每份 bundle 私有变量里。重入销毁的公开提前返回和真实清理结束不是同一时点。

这里首先要区分应用版本和 core 版本：普通子应用只使用注入的生命周期与通信对象、没有再次加载 core 时，不存在两份 core 争用操作槽的问题。同一页面独立打包多份 core，或子应用加载 core 管理嵌套应用时，才可能通过 inject 共享操作槽；不同版本并不是共享发生的必要条件，同版本多副本也需要正确协调。

本次对比的本地 Wujie（c4593299）也共享实例/配置注册表：`common.ts:12` 复用 `__WUJIE_INJECT.idToSandboxMap`，`sandbox.ts:657` 将 inject 传给嵌套应用。销毁时 `common.ts:38` 移除实例，没有 setupApp 配置就删除条目，有配置则保留配置。它没有 Jieshu 的 operation-intent 表；`index.ts:375` 对不存在的应用直接结束，`index.ts:306` 的 idle preload 到执行时才查实例是否存在，尚未创建的预加载没有同等的全局取消记录。因此 Wujie 不需要回收这类操作槽，也没有本方案引入的使用计数兼容问题。这些结论针对本次本地对照源码，不是对官方所有版本混用能力的承诺。

之所以考虑旧版，是因为新方案若要求登记使用计数，现有 core 不会登记。比如旧副本排队的 preload 已观察某条记录，新副本销毁完成就删除它，旧 preload 随后会将自己判为失效。这是修改共享状态清理规则时的具体回归风险，不是要求先做一个完整的多版本兼容系统。第一步去冗余和第三步弱表优化不依赖它；操作槽方案优先验证现有并发契约，混用时保守保留未知使用者的状态，不以所有应用同步升级为前提。

如需进一步保证混用情况下也能主动回收，下面是待验证的设计选项，复杂度中高，不作为本轮其他优化的前置条件：

- 默认保守兼容现有共享状态协议，优先保证操作行为，不贸然删除旧版可能仍在使用的记录。此模式可能保留部分内存成本。
- 对支持新协议的版本统一登记、释放和取消语义，提供版本化的协议入口；仅“加一个版本号”不能补上旧代码缺失的使用登记。
- 不声称能够自动识别任意旧 observer：旧版可能只读取新版创建的记录，而没有留下可检测的登记。混用兼容策略需要明确配置或可证明的能力协商，不能只检查槽是否带新字段。
- 测试新主旧子、旧主新子、两份不同版本 core、多应用交错 start/preload/destroy/refresh，以及旧操作迟到和重入。先从当前 bc688b2 与下一版这一个明确组合开始，再扩大支持范围。

建议分开验收“混用行为兼容”和“混用时全部记录可回收”。前者可以先做，后者不能在不改旧代码、也没有兼容层的前提下直接保证。常量去冗余、弱表容量优化可独立推进，不必等待操作协议完成。

必测：不存在名称销毁、真实 start/destroy、返回的 destroy handler、控制器 release、销毁中排队 preload、并发 start/refresh、旧操作迟到、异常/重入、两份 core 与跨 realm 共享。验收是操作结束后无待用槽，独立名称增长不再保留记录，同时全部竞态行为保持。

### 第三步：调整 instanceof 状态的存放位置，释放弱表容量

优先评估让状态随现有补丁/构造器一起生存，或按 realm 划分弱表，避免用一张模块级宽表容纳所有曾启动的子 realm。预期目标是去掉无应用时仍保留的空容量，尚未量出修复后净收益。

需要保留自定义子类、同一构造器在多个窗口的别名、共享宿主构造器 facade、重复 patch、交错 release、构造器被冻结/被覆盖等行为。不能直接按 targetWindow 分片就认为正确：同一构造器可能在两个窗口被复用，两张表若各自覆盖 Symbol.hasInstance 会丢失注册。落地后必须重新采集真实挂载/销毁快照确认容量释放。

### 第四步：减少必经实现体积；按需分包是有取舍的备选

针对解析、资源处理和生命周期中的重复逻辑逐段重构，沿用既有行为测试，记录每次 raw/gzip/加载/堆的增量。当前没有证据能一次安全消除剩余约 42 KB raw 差距，应分段验证，不承诺全功能包必定持平。

若尝试轻入口加延迟加载运行时，可以降低从未启用微前端的页面的核心加载和空载内存。但它会把下载、解析和初始化转移到首次 startApp；全量字节不一定减少，冷启动还可能增加请求。必须一起测入口加载、首次子应用 ready、加载后总字节和堆，不能仅靠 coreLoad 变小宣称优化完成。普通 ESM tree shaking 已经在用，简单拆文件也不会自动减少必需代码。

## 5. 验收与本轮交付

建议先落实第一步和内存状态回收的设计验证，再决定是否需要分包。每项优化单独留前后数据，至少保留同轮 Wujie 对照、30 次加载的中位数/P95及区间、纯加载/挂载后/静置后堆；不得靠将成本移到首次启动或关闭正确性检查通过指标。

本轮实际完成 8 种统一构建和独立 source map 复算、4 种候选方案的构建实验、120 次核心加载、12 次 trace，以及 12,000 次公开空销毁调用。诊断脚本通过语法、ESLint 和格式检查。具体环境、哈希、原始记录与命令见[诊断目录](../../benchmarks/comparison/results/2026-09-09-footprint/)。大体积 bundle/source map/trace/heap 快照放在忽略的 test-results，未纳入交付文件。

核心仍是已验证的 bc688b2，没有把未验证的协议或兼容变更写进核心；本轮不重复运行未修改 core 的整套回归，也没有创建新提交。
