# 核心加载：第一轮等价精简

日期：2026-09-09。接续[原因分析](./core-load-causes.md)，目标是缩小差距。优化前固定为 `557c51d` 的完整生产 ES2018 IIFE，优化后保留全部公开入口和相同编译目标。

## 本轮修改

- 控制器共用 start/refresh 的前置检查、运行和状态收尾。保留原有差异：过期 start 在移除 pending 名称后清理，过期 refresh 在清理完成后移除；没有新增 await 或 Promise 包装层。
- HTML、脚本和样式共用请求文本及错误报告流程。保留两个独立 try/catch，HTTP 状态检查仍在其外；HTML 日志使用 url，脚本和样式使用 src；loadError 抛错不会被重复报告。
- 三个私有 AssetCache 共用原型方法，减少重复方法闭包。缓存对象不导出，所有调用都保留实例接收者，缓存身份、取消和旧缓存记录保持原有行为。
- 模板和资源入口共用同一份属性转义及样式属性名单。保留属性值的编码及原生 link 回退行为。

这轮不延后缓存或入口初始化，不新增动态加载。这样无需把核心导入成本转移到第一次子应用启动，也不引入新的异步边界。

## 检查中发现的问题

1. start/refresh 看起来重复，但过期清理的 pending 状态和异常处理位置不同。直接合并会改变 dispose 的取消行为；本轮保留差异，并新增成功/拒绝的回归测试。
2. 资源请求若使用一个大 try/catch，会二次报告 loadError 自身抛出的异常，或改变 status getter 抛错行为。本轮保持原有异常边界，做差异检查和公开入口测试。
3. 内部箭头方法改为原型方法会失去自动绑定。逐个检查了调用点，当前不存在脱离实例的调用；另补同 URL、同 fetch 的三类缓存隔离测试。
4. 旧启动汇总脚本只接受 Jieshu/Wujie。新增可选冻结 Jieshu 基线，校验 SHA 和构建元数据，同轮轮转三组；用独立前后汇总脚本，不将跨轮绝对耗时差当作收益。

5. 初始 A/B 中服务器对当前包逐请求编码字符串，对冻结旧包直接发送 Buffer，导致发送路径不对称。该轮 UTF-8 总加载增加 0.20 ms，请求/响应也增加 0.20 ms，解析/执行诊断反而下降。原始记录保留为测量问题证据；修正为所有包在采样前统一 UTF-8 Buffer 后重新采样，初始总加载差值不用于评价优化。

## 结果

本轮保留的是体积和固定开销的小幅精简。**总加载中位数略低，但区间包含零，尚不能确认总加载稳定提速。** 核心功能回归通过；首次启动尾部经追加复测未出现持续的大幅退化。

| 指标                      |    优化前 |    优化后 |               变化 |
| ------------------------- | --------: | --------: | -----------------: |
| 完整核心 raw              | 108,581 B | 107,474 B | −1,107 B（−1.02%） |
| 完整核心 gzip             |  32,708 B |  32,578 B |   −130 B（−0.40%） |
| UTF-8 核心总加载中位数    |   4.40 ms |   4.30 ms |           −0.10 ms |
| CDP ScriptDuration 中位数 | 0.5000 ms | 0.4625 ms |         −0.0375 ms |
| 核心加载引入的 GC 堆增量  | 217,384 B | 216,100 B |           −1,284 B |

修正发送方式后，三版本 × legacy/UTF-8 × 60 轮，共 **360 条普通观测**；另采 **42 条 trace**。UTF-8 总加载前后配对差值 95% bootstrap 区间为 **[−0.25, +0.05] ms**，ScriptDuration 为 **[−0.065, −0.009] ms**。后者包含相同测量探针的执行，不等于纯业务执行时间。Wujie 同轮总加载中位数 3.20 ms，Jieshu 仍有明显差距。

六个完整功能变体另做同轮 UTF-8 诊断，共 **360 条普通观测 + 42 条 trace**。缓存方法共享单独减少 608 B GC 堆，ScriptDuration 减少 0.039 ms，区间 [−0.063, −0.009]；其余单项主要减少体积和堆内存，未确认总加载收益。组合的总加载差值为 −0.10 ms，区间 [−0.15, +0.10]，同样不能宣称稳定提速。不同改动的收益不可简单相加。

## 首次启动与内存

首次启动四场景，每个版本各 30 轮，共 **360 条观测全部完成、无页面错误**。以下差值均为优化后减优化前：

| 场景         | ready 中位差 |      配对 95% 区间 |
| ------------ | -----------: | -----------------: |
| 冷启动       |     −0.45 ms |  [−0.95, +0.70] ms |
| fiber 冷启动 |     +0.20 ms |  [−0.20, +0.90] ms |
| 五应用并发   |     −0.80 ms |  [−2.05, +0.55] ms |
| CPU 4x       |     −6.90 ms | [−16.60, +6.70] ms |

这些区间不证明所有情况等价。原 30 轮 CPU 4x 的 P95 从 170.145 增至 183.395 ms，差值 +13.25 ms，P95 差值配对区间 [−6.57, +25.70]。因此单独追加 90 轮，三版本 **270/270 条观测通过**，不与原轮合并：

| CPU 4x 追加 90 轮 |     优化前 |     优化后 |       差值及配对 95% 区间 |
| ----------------- | ---------: | ---------: | ------------------------: |
| ready 中位数      |  162.55 ms |  162.75 ms |   +0.20 [−1.00, +1.25] ms |
| ready P95         | 166.155 ms | 166.755 ms | +0.60 [−0.685, +2.555] ms |
| API P95           | 142.210 ms | 142.500 ms |  +0.29 [−1.20, +1.195] ms |

原先 +13.25 ms 的尾部差距未在追加采样中复现；没有看到持续的大幅尾延迟退化，但不能排除小幅或罕见变化。P95 使用针对 P95 差值的配对区间，没有挪用中位数区间。冷启动原轮 P95 也有 +1.73 ms 波动，原始分布一并保留，不只展示较好的指标。

内存对照每版本 1 轮，依次执行首次挂载、30 次同资源及 30 次不同资源的挂载销毁、缓存清理与静置、五应用保活及最终清理。三版本均无页面错误。当前相对旧版：首次挂载 **+48 B**，五应用活跃 **−8,260 B**，最终清理静置后 **−1,104 B**；最终两版均为 1 document、11 nodes、3 listeners。单轮不能估计稳定区间，也不能据此承诺所有活跃场景内存下降。

## 验证与边界

- 核心单元测试：55 文件，**564/564 通过**（本轮增加 35 项）；覆盖率 statements 79.14%、branches 72.25%、functions 83.91%、lines 80.96%。
- 核心浏览器测试：**137/137 通过**。
- React/Vue 示例集成测试：**77/77 通过**。
- 三轮稳定性对比：Jieshu **48/48**，Wujie **42/48**；Wujie 的 start-destroy-race、same-name-concurrent-containers 各失败三次，与此前类型一致。
- 类型检查、生产构建、只读 ESLint、格式及 diff 检查通过；基线加载和前后汇总工具的 14 项合成测试通过。只修改核心，不涉及适配包源码。
- 控制器新增测试先在原实现、再在新实现运行，两边 22/22 通过；请求处理另有 312 组隔离差异检查，比较异常身份、调用/微任务顺序、日志字段和 receiver。

性能只覆盖本机 headless Chromium、ES2018 完整 IIFE、未压缩正文和本地 HTTP；没有外网、其他浏览器、生产 ESM 消费、总进程 RSS 或真实移动设备数据。CPU 4x 为模拟降速。上下文隔离不等于冷浏览器进程，后台活动仍可能影响尾延迟。统计按同轮配对、固定种子 5000 次重采样，不将嵌套 trace 耗时相加，不混合修正前后发送方式的数据。
