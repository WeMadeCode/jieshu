# Wujie / Jieshu 性能与稳定性对比报告

日期：2026-09-09。**本次结果不支持 Jieshu 在启动、内存和所有场景稳定性上全面优于 Wujie。** Jieshu 的明显优势是频繁创建/销毁时的即时回收；它同时承担更大的核心包、稍高的稳态堆占用，以及本轮多应用并发和 CPU 降速条件下更高的启动成本。双方都存在启动取消后的 Loading 清理缺陷。

计划见 [PLAN.md](./PLAN.md)，复现命令见 [README.md](./README.md)，问题的复现、证据与建议见 [ISSUES.md](./ISSUES.md)。本轮只新增对比脚本、数据和文档，没有修改两个框架的实现或适配包，也没有创建提交。

## 1. 被测对象与范围

| 项目            | Wujie                                    | Jieshu                                   |
| --------------- | ---------------------------------------- | ---------------------------------------- |
| 本地 core 版本  | 2.1.0                                    | 0.0.5                                    |
| 完整 commit     | c45932998c0602f34454df8d3e29f4d33a38446a | b0c73aaa944ea8603c6fb13f3126e341b320d2cb |
| 生产压缩 bundle | 65,660 B                                 | 108,242 B                                |
| gzip 体积       | 19,802 B                                 | 32,603 B                                 |

运行环境：Apple M1 Pro，8 核，16 GiB，macOS 26.6.2 / Darwin 25.6.0，Node 26.7.0，Playwright 1.62.1，Chromium 151.0.7922.34，1280×800，headless。开始时系统负载约 2.79 / 2.83 / 2.89，桌面后台活动没有完全隔离。

两份 core 都从当前源码以 **Vite 8.2.2、ES2018、生产压缩 IIFE** 重新构建。没有使用可能过期的 dist；也没有将不同 UI 示例的加载时间直接相比。这控制了构建方式差异，**不是 npm 官方发布包对比**。本地 Wujie 的原生构建使用不同的 webpack/Babel/ES5/UMD 设置；本轮未联网核实该本地 commit 与当前上游的关系。

同一子应用包含 300 个列表节点、4,000 个 JS 对象、点击计数、路由、总线和生命周期。接入只兼容两框架不同的全局变量名。主子页面位于不同 localhost 端口，资源允许 CORS；两边显式使用相同选项。默认 `fiber:false`，另列 `fiber:true`。

正式采样时间为北京时间 **15:18:50–15:23:25**。总计 **646 条正式观测**：540 个启动样本、10 轮内存序列、96 次稳定性检查；其中 12 次稳定性失败完整保留，没有重试后抹除失败。

## 2. 启动：常规切换接近，Jieshu 多应用并发与降速启动更慢

每框架每场景 30 个新 context 样本；另有每框架每场景 2 轮不参与统计的预热，共 36 次。所有 540 个正式启动样本均成功。

下表单位为 ms，单元格为 **中位数 / P95**。计时从调用 `startApp` 开始，到子应用报告 ready、目标容器的 ready DOM 可见，并经过两个主页面 rAF 结束。核心 bundle 已单独加载，因此这里的“冷启动”是冷的子应用与框架资源缓存，**不是首次访问网页的端到端耗时**。

| 场景                  | Wujie           | Jieshu          | Jieshu 中位数差异 |
| --------------------- | --------------- | --------------- | ----------------- |
| 冷启动，fiber 关闭    | 37.25 / 40.45   | 36.60 / 39.54   | −1.74%            |
| 冷启动，fiber 开启    | 53.60 / 61.62   | 53.10 / 109.61  | −0.93%            |
| 销毁后缓存重建        | 15.35 / 15.90   | 14.80 / 15.61   | −3.58%            |
| 单例卸载后重挂        | 16.75 / 18.10   | 16.75 / 18.01   | 0.00%             |
| 保活切回              | 16.70 / 17.31   | 16.65 / 17.62   | −0.30%            |
| 预执行后进入          | 16.50 / 16.66   | 16.55 / 16.66   | +0.30%            |
| 五应用并发，全部就绪  | 71.90 / 73.02   | 80.90 / 87.27   | **+12.52%**       |
| 各资源响应延迟 150 ms | 484.60 / 495.64 | 485.95 / 500.16 | +0.28%            |
| CPU 四倍降速          | 170.20 / 177.66 | 178.90 / 182.92 | **+5.11%**        |

固定 seed 的 5,000 次独立 bootstrap 给出中位数差 `Jieshu − Wujie` 的 95% 区间：五应用并发 **[7.20, 10.30] ms**，CPU 降速 **[4.40, 12.25] ms**。同 round 配对重采样也保持正值。这是当前负载下可重复采样到的成本差异，不代表所有业务都会有相同百分比。

冷启动和缓存重建的就绪中位数分别低 0.65 ms、0.55 ms；虽然本轮区间不跨零，绝对差很小，而且 ready 指标受渲染帧节奏影响。API 本身的中位数并未同步变快：冷启动 Wujie 27.20 ms / Jieshu 27.45 ms，缓存重建 10.25 / 10.90 ms。因此不把亚毫秒就绪差概括为全面启动提速。

冷启动场景中，单独加载 core 的中位数为 Wujie **5.40 ms**、Jieshu **6.50 ms**。Jieshu 的 gzip 包大 **64.64%**；本地服务器实际提供未压缩 JS，gzip 只是体积分析，未模拟 CDN 压缩传输。不同区间的中位数不能直接相加成为端到端中位数。

预加载不是零成本：预执行准备中位数 Wujie 37.65 ms / Jieshu 36.70 ms，随后进入约 16.5 ms。保活与单例准备成本也单独保存在数据中。资源延迟场景是服务器对 HTML/JS/CSS 各延迟 150 ms，不是公网带宽/RTT 模型；CPU 降速不等于某款手机。

Jieshu 在 `fiber:true` 下的 P95 明显高于 Wujie，是需要复查的长尾观测。每组只有 30 个样本，桌面后台活动未完全受控，且没有执行 CPU profile；**尚不能把长尾归因到特定调度实现**。

## 3. 内存：Jieshu 即时回收更好，Wujie 稳态占用更低

每框架 5 轮独立 context，每轮先记录空页/core/单应用，再进行同 URL 30 次创建销毁、不同资源 URL 30 次创建销毁，随后清缓存、静置、挂载五个保活应用并销毁。所有 10 轮完成，无页面异常。

下表为强制 GC 后 JS 堆的跨轮中位数，单位 **MiB**；这不是浏览器总内存或 RSS。

| 阶段                   | Wujie  | Jieshu | 解释                               |
| ---------------------- | ------ | ------ | ---------------------------------- |
| 只加载 core            | 0.660  | 0.714  | Jieshu 基础成本略高                |
| 首个应用挂载           | 4.010  | 4.179  | Jieshu 高约 4.2%                   |
| 首个应用销毁，立即 GC  | 3.671  | 2.735  | Jieshu 更早释放实例                |
| 同 URL 30 次销毁后     | 35.430 | 3.151  | Wujie 短时保留较多文档             |
| 再更换 URL 30 次销毁后 | 67.050 | 3.290  | 此阶段承接前 30 次，不是独立起点   |
| 清缓存后静置 5.5 秒    | 2.923  | 3.225  | Wujie 延迟保留明显回落             |
| 五应用保活挂载         | 9.894  | 10.515 | 已先静置，避免混入前段 iframe 残留 |
| 五应用失活             | 9.894  | 10.511 | 保活按设计继续持有状态             |
| 五应用销毁，立即 GC    | 9.879  | 3.231  | 回收时机不同                       |
| 最终静置 5.5 秒        | 2.924  | 3.231  | Jieshu 稳态高约 10.5%              |

同资源第 30 次销毁后，Wujie / Jieshu 的 `Documents` 分别为 **32 / 1**；两个阶段共 60 次销毁后为 **62 / 1**。静置 5.5 秒后双方都恢复到 **1 个 Document、11 个 Node、3 个 JS 监听器**；与 core 基线相比仅多一个宿主 Node，并未残留子文档。最终双方也回到该计数。

源码中 Wujie iframe 初始化的 5 秒兜底定时器在正常完成时没有取消，闭包继续引用子窗口；Jieshu 会取消。这是延迟释放的具体源码线索，与等待后的回落相符，但没有堆保留路径快照，不能精确归因全部差额。

因此，**可以确认 Jieshu 在本轮高频创建/销毁时的短时堆占用更低，不能确认它的稳态内存更低，也没有证明 Wujie 永久泄漏。** 不同 URL 阶段还叠加了时间与缓存变化，不能把其全部增长归因于资源缓存。

## 4. 稳定性：常规场景均通过，并发取消双方都有缺陷

16 个场景各重复 3 轮。两框架各 **42/48 次通过**；按不同场景看，各有 14/16 项全部通过。这个人为选择的场景比例不是生产故障概率，也不是覆盖率。

共同通过的 14 类检查包括：渲染/点击/生命周期顺序，props 与 bus，JS 与 CSS 隔离，双应用独立状态，销毁重建，保活，路由同步开/关，异步卸载完成，预执行后进入，动态脚本/样式及保活后样式，脚本 404 通知与恢复，以及 fiber 开启交互。

| 并发压力场景                 | Wujie，3 轮                                              | Jieshu，3 轮                        |
| ---------------------------- | -------------------------------------------------------- | ----------------------------------- |
| 资源加载期间 destroy         | 3/3 内部 `null.protocol` 拒绝；3/3 Loading 残留          | 请求正常结束；3/3 Loading 残留      |
| 同名应用在不同容器重叠 start | 3/3 旧请求内部 `null.protocol` 拒绝；3/3 旧 Loading 残留 | 两请求正常结束；3/3 旧 Loading 残留 |

并发用例允许旧请求以明确的 `AbortError` 取消。这里 Wujie 返回的是访问清理后状态的内部 `TypeError`。两框架的 DOM 归属检查没有发现重复挂载：destroy 后 ready 为 0，同名替换后旧容器 ready 为 0、新容器为 1。拒绝由测试通过 `Promise.allSettled` 捕获，`pageErrors` 为空，不能描述为已经发生未捕获页面异常。

新增 Loading 断言后，两个并发用例都会在缺陷处失败，因此正式失败样本没有继续到末尾的新实例点击断言；常规双应用/交互用例仍覆盖了正常交互。不能因新实例已 ready 就额外宣称竞争后的完整交互均已验证。

两种输入属于健壮性扩展，并非假设 Wujie 文档承诺“全部并发调用必定成功”。但遗留遮罩和内部空指针有具体用户可见影响，已经记录为可修复问题。


本次复用已安装依赖，没有进行安装；直接用 Node 调用本地 CLI，避开环境中的 pnpm 版本不一致。Chromium 第一次在沙箱内启动因 macOS MachPort 权限失败；改为已授权的本地执行后运行成功，此环境失败没有计入框架失败数。原生测试日志保存在忽略目录 `test-results/comparison-{jieshu-unit,jieshu-browser,wujie-unit}.log`，结论和结果另保留在本报告及 [validation.json](./results/2026-09-09/validation.json)。
